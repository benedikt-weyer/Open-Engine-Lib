# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Open Engine Lib: an open-source, Linux-focused desktop app for managing an Engine DJ library. It is two programs in one Cargo workspace that talk over versioned gRPC; see `docs/architecture.md` for the details, `docs/engine-library-format.md` for the Engine database format and `docs/soundswitch-format.md` for what is known (and only inferred) about SoundSwitch's project files.

- `open-engine-lib` (`src/`, the UI) is built on the [iced](https://iced.rs) GUI toolkit (0.14, Elm-style `State` / `Message` / `update` / `view`). `src/main.rs` holds the app state, the messages, `update`/`view` and `handle`, which only routes a message to the function of its feature in `src/handlers/` (`settings`, `sync`, `playlists`, `library_sync`, `import`, `library`, `playback`, `cues`, `loops`, `origin_prefix`, `repair`, `track_menu`; each is a `match` over the messages it owns, with the guard arms before the arms they fall through to; a new message needs an arm in its handler and a place in `handle`, which has no wildcard so the compiler says where) — one huge function was slow to optimise in a release build; the other modules below are in `src/data/` (the logic that does not draw: `analysis_queue`, `backend`, `clock`, `colors`, `columns`, `config`, `controller`, `covers`, `cues`, `drives`, `i18n`, `local_folders`, `loops`, `model`, `mpris`, `reachable`, `recent`, `session`, `waveform`) or `src/views/` (the widgets and windows: `browser`, `cue_bar`, `cue_editor`, `deck`, `error_text`, `folder_menu`, `import_view`, `library_sync_view`, `loop_bar`, `loop_editor`, `menubar`, `navbar`, `origin_prefix_dialog`, `player_bar`, `playlist_dialog`, `progress_view`, `repair_view`, `settings`, `sidebar`, `smart_editor`, `sync_view`), each folder with a `mod.rs` that lists its modules; `main.rs` imports every one of them (`use data::{config, …}`), so they are still `crate::config`, `crate::deck` and so on, and a new module needs a line in its folder's `mod.rs` and in that import; `backend.rs` starts the backend process and is the gRPC client (`Backend::about(kind)` tags its requests with the library they are about; `State::backend()` does so for the shown one); `State::library` is the shown library and `State::parked` the open one of the other kind (an Engine library and a folder of music are open together, one of each at most; `make_room_for`, `switch_libraries`); `browser.rs` (playlist tree and virtualised track list; clicking a column header sorts it ascending, descending, then back to the playlist order, and the tracks of an ordinary playlist are numbered; when the columns are wider than the window the header and rows scroll sideways together, with the horizontal scrollbar under the list), `player_bar.rs`, `navbar.rs` and `settings.rs` are views; `model.rs` is the UI's copy of the open library, `covers.rs` the bounded cache of cover images fetched for what is on screen, `recent.rs` the recently opened libraries and `session.rs` the last session (library, playlist, song, position; both saved in the user state dir; `State::restore_session` and `snapshot` in `main.rs` apply and capture it) and `columns.rs` the widths of the track list's columns (resized by dragging) and which columns the user hid (the "Columns" menu over the list; both saved in the user state dir), `mpris.rs` the desktop's media interface (MPRIS over D-Bus with `zbus`, Linux only; a subscription that serves `org.mpris.MediaPlayer2.open-engine-lib` and gives the UI a handle to push the playing track, its cover (written to a file in the runtime dir for `mpris:artUrl`) and the state into, and turns media keys and `playerctl` into messages; `handlers/mpris.rs` maps those to the player's messages and `State::tell_desktop`, run after every update, sends what changed), `controller.rs` what the backend reports of the DJ controller (the UI has no MIDI code: the backend listens, learns and acts, and the Settings page only shows it and sends commands, among them the choice between profiles of bindings: the library process's `controller.rs` keeps them, with the built-in ones for the SC LIVE 4 in `controller/presets.rs`), `cues.rs` the cues fetched for the tracks played (and the position text format), `cue_bar.rs` the row of eight cue pads under the waveform and `cue_editor.rs` the window for editing the playing track's cues ("Edit cues…"), `loops.rs`, `loop_bar.rs` and `loop_editor.rs` the same for the saved loops, `local_folders.rs` the folders of music added to the sidebar's "Local music" section (saved in the user state dir; a folder is opened as a library of kind `Folder` in `model.rs`, with the Engine-only columns, buttons and pads left out), `library_sync_view.rs` the window for syncing the playlists to another library ("Sync to…" in the sidebar: pick a recent library, a drive's library or one added by its folder, see the differences, write them), `origin_prefix_dialog.rs` the window for changing the folder the saved origins start with ("Change origin folder…" next to "Save locations as origins": it shows the folder all origins are in, takes the folder to put there, typed or picked, and changes them in the working copy without checking that files are at the new place), `track_menu.rs` the context menu of a track of the list (right click: delete from the playlist shown, delete from the library; `right_click.rs` is the wrapper that says where the right click was), `folder_menu.rs` the menu of a folder of the playlist tree of a folder of music (right click: "Import as playlist…"), `import_view.rs` the window that takes such a folder to an Engine library as a playlist (pick the library, the playlist's title, whether names are put in order strictly (1, 10, 11, 2) or by their numbers (1, 2, 10, 11), with a preview of the resulting order, whether the files are copied and the new tracks analysed; `handlers/import.rs`; what the backend does is `folder_import.rs`), `analysis_queue.rs` the tracks that wait to be analysed one after the other (the toast says which of how many, with a button that drops the rest; started by the track menu's "Analyse the N unanalysed tracks of this list" and by the import), `playlist_dialog.rs` the window for adding, renaming and deleting an ordinary playlist ("New playlist…" under the tree, and ✎ and × next to the shown playlist), `smart_editor.rs` the window for adding a smart playlist or changing one's rules (the ✎ button next to a smart playlist, and "New smart playlist…" under the tree), `sync_view.rs` the sync window (the differences, and the button that writes them to the source), `menubar.rs` the File menu (Open, Save as, Exit), `sidebar.rs` the left side (playlists, the connected USB drives and recent libraries) and `drives.rs` the detection of those drives and of an `Engine Library` at their root (Linux only: mountinfo plus `/sys/dev/block`; rescanned every few seconds off the UI thread), `deck.rs` the waveform display (draws the cues and loops over both views; dragging the zoomed one scratches the track; a custom widget for the zoomed scrolling waveform with beat lines, whose geometry is drawn once per 12-second piece of the track, kept as cached geometry and only moved with the renderer's translation as the track plays, because tessellating the outline anew for every frame made frames late; plus the clickable overview, whose waveform is cached the same way, and a menu for the color scheme; `colors.rs` has the color schemes) and `waveform.rs` its data (beat positions, overview pooling, a small cache) and `clock.rs` the smoothed playhead clock. `i18n.rs` loads UI strings from `locales/<code>.yaml` (English and German; add a key to the `Strings` struct and to every locale file, and tests check completeness and matching `{placeholders}`; fill them with `i18n::fill`; views read the language from `ConfigStore::effective()`). The UI has no SQLite or audio code.
- `open-engine-backend` (`backend/`) is two programs. The library process (`backend/src/main.rs`, binary `open-engine-backend`) reads the Engine library; the UI spawns it, it exits when the UI goes away, and it is the only thing the UI talks to. It starts the audio process (`backend/src/audio/`, binary `open-engine-audio`: `engine.rs` is the playback queue plus the thread that owns the audio device, `player.rs` the rodio output behind a trait, `scratch.rs` scratching (a window of the track decoded and played from a position that follows the hand, so it sounds at the speed of the hand, backwards too; `BeginScratch`/`MoveScratch`/`EndScratch`, used by dragging the zoomed waveform and by the controller's jog wheel), `waveform.rs` the waveform analysis, `service.rs` the `AudioService`) and passes the UI's playback and waveform requests on to it over gRPC (`audio_client.rs` starts it and holds the connection; `service.rs` looks up the files). The audio process knows no libraries, talks only to the library process and exits when that goes away. Only the library process links SQLite and only the audio process links ALSA (for audio and for the MIDI of DJ controllers: `audio/midi.rs` reports what the hardware sends over `WatchMidi`; the library process's `controller.rs` holds the learned bindings and `service/controller.rs` carries the actions out (and turns the jog wheel's 14-bit positions into scratch moves) and serves `ControllerService` to the UI; see `docs/architecture.md`). `progress.rs` is how far a running sync has got (the copy loops report to it in chunks; the UI asks `GetProgress` every quarter second while a sync writes and `progress_view.rs` draws the bar), `new_library.rs` makes an empty library (the schema of the open one, no rows) for "Sync to…" a place without one, `track_sync.rs` is the track part of that sync (stars, paths, copying the files into an `Engine-Tracks` folder beside the other library in `Artist/Album` folders with exFAT-safe names, adding tracks the other library lacks, with their `Artwork` covers and, if asked, `Stems` files), `mirror.rs` makes the playlists and smart playlists of another library the same as the open one's (works on a copy of the other library's `m.db`, which a diff throws away and a push installs after keeping the old one), `repair.rs` ("Repair library…": deletes the old `open-engine-lib-backup` folder from a library's `Database2` and moves its origins file to the `open-engine` folder beside `Engine Library`; `repair_view.rs` is its window), `origins.rs` (kept in `open-engine/open-engine-lib.db` beside the `Engine Library` folder, not in it; which also finds the folder all origins share and replaces a leading folder in them, for `GetOriginPrefix` and `ReplaceOriginPrefix`) is Open Engine Lib's own database (`open-engine-lib.db`, copied to the working copy's `Database2` and synced with the other databases, and written to another library by the playlist sync) with the saved origin of tracks, keyed by Engine's `(originDatabaseUuid, originTrackId)` so a track copied to another library has the same origin there (the `MigrateOrigins` call saves the location of every track that has none; the track list's Origin column shows it), `cache.rs` copies the library's databases into a cache so nothing works on the library in place (audio files are not copied), `folder.rs` scans a plain folder of music into tracks (tags read with `lofty`) and a tree of playlists for `OpenLocalFolder`, `tag_cache.rs` remembers what was read from each file (SQLite `tags.db` in the folder scratch dir under the cache root, keyed by file path and only used while the file's size and modification time match, so opening the folder again reads only new or changed files), `slot.rs` makes the library a request is about known to the handlers (two are open at once: `engine` and `folder` slots of `service.rs`), `library.rs` reads tracks and playlists (smart playlists too, with `smartlist.rs` working out their tracks) and reads and writes cues and loops (`cues.rs` and `loops.rs` are the codecs of Engine's `quickCues` and `loops` blobs) and serves cover images and beatgrids (`beatgrid.rs` decodes Engine's `beatData`), `soundswitch.rs` works out from the drive's SoundSwitch projects which tracks have lighting (reverse engineered, see `docs/soundswitch-format.md`), `track_analysis.rs` turns what the audio process found in a track (beats, key) into Engine's beatgrid, track data, tempo and key (`Library::apply_analysis` writes them to the working copy and records in `origins.rs`'s database that Open Engine Lib made the analysis, which the track list's "Analysis origin" column shows; the context menu's "Analyse track" starts it, with a progress toast, `views/toast.rs`), `name_order.rs` puts the files of a folder in order by name, strict or natural, for the import and its preview (`PreviewFolderImport`), `folder_import.rs` imports a folder of the open folder library into an Engine library (`ImportFolderAsPlaylist`: tracks without an analysis but with their embedded covers (as `Artwork` thumbnails), optionally the files copied to `Engine-Tracks`, and a playlist; on a copy of the library's `m.db` like `mirror.rs`, which it shares its install and backup code with), `sync.rs` compares the working copy with the source and writes it there (with a backup, and guarded against a busy or outside-changed source) or the other way round (`pull`: the source replaces the working copy; both sync windows and `mirror.rs` work in both directions), `save.rs` clones the library to a new place ("Save as", rewriting the track paths), `service.rs` implements the gRPC services for the UI.
- `open-engine-api` (`api/`) holds `proto/openenginelib/v1/*.proto` and the generated code. Within `v1` only make additive changes; a breaking change is a new `v2` package. The `.proto` files are compiled by `protox`, so `protoc` is not needed.

Smart playlists are shown in the playlist tree with an icon, their rules are evaluated in the backend (`smartlist.rs`, which also writes them back as Engine's JSON) and they can be added (top level only) and edited, in the working copy like a rating ( only `genre LIKE` has been seen in a real library, and writing them has not been tried on a real player; see `docs/engine-library-format.md`). The playback history is not shown yet, and the key column is left out (the Engine key numbers are inferred, see `docs/engine-library-format.md`).

## Environment

Development uses a Nix flake (`flake.nix`) activated by direnv (`.envrc`: `use flake` + `PATH_add scripts`). The dev shell provides the Rust toolchain and the runtime libraries iced loads dynamically (Wayland, X11, Vulkan, GL, xkbcommon) via `LD_LIBRARY_PATH`. Run `direnv allow` once, or prefix commands with `nix develop --command` if you are outside the shell. Without the shell the app may build but fail to open a window. The audio process links ALSA (`alsa-lib`, also in the dev shell and the Nix package) and, for the analysis of tracks, libKeyFinder (`libkeyfinder`, which brings FFTW; also in the dev shell and the Nix package, so reload direnv after pulling) and needs `pkg-config`. Without libKeyFinder, build with `--no-default-features`. `Cargo.toml` patches `rten-gemm` with `vendor/rten-gemm` because the Nix toolchain cannot compile the original (see the note there).

## Commands

- `run [library path]` (`scripts/run`): `cargo build` (the UI, the library process and the audio process; our own code is not optimised, the dependencies are, so it builds quickly), then runs `target/debug/open-engine-lib`, forwarding args to it. `run-optimized [library path]` (`scripts/run-optimized`) does the same with `cargo build --release` and runs `target/release/open-engine-lib`, for judging how smooth the waveform and the track list are. The UI finds the backend next to its own executable, so a plain `cargo run` needs `cargo build -p open-engine-backend` first (that builds the audio process too, which the library process finds next to itself).
- `help` (`scripts/help`): lists developer commands. Keep it in sync when adding scripts or commands. In bash, `help` is a builtin, so run `scripts/help` there.
- `cargo check` / `cargo clippy` / `cargo fmt` (add `--workspace` to cover the backend and API crates too)
- `cargo test --workspace` (single test: `cargo test <name>`): config and i18n in the UI, the queue/cache/library code in the backend, and `backend/tests/grpc.rs`, which starts the real backend and drives it over gRPC. `plays_from_a_real_library` there is `#[ignore]`d: it plays real audio from a real library, see `docs/architecture.md`.
- `nix flake check`: validates the flake (only x86_64-linux is evaluated locally)
- `nix build`: builds the Nix package (`nix/package.nix`), which contains all three executables

The flake also exports `packages`/`apps` (default), `overlays.default` and `nixosModules.default` (`programs.open-engine-lib.enable`) for NixOS installs. `nix/package.nix` sources only `Cargo.toml`, `Cargo.lock`, `src`, `api`, `backend`, `locales` and `packaging`, and patches the runtime library RPATH (windowing libraries on the UI, ALSA on the audio process), so add any new top-level build inputs to its fileset.

Newly added files must be `git add`ed (at least `-N`) before Nix flake commands can see them, because flakes only read tracked files.

The root `Cargo.toml` builds dependencies with `opt-level = 2` in debug builds (`[profile.dev.package."*"]`): the audio decoders are too slow unoptimised for waveform analysis to be usable.

## Configuration

`src/data/config.rs` implements layered config so it works with declarative (Nix) setups. The base TOML file is the first found of `$OPEN_ENGINE_LIB_CONFIG`, the user config dir, then `$XDG_CONFIG_DIRS` plus `/etc/xdg`. If it is writable or absent, the app edits it directly. If it is read-only (e.g. generated by the NixOS module's `programs.open-engine-lib.settings` into `/etc/xdg/open-engine-lib/config.toml`), edits go to `overrides.toml` in the user state dir and are merged on top; "Reset to underlying config" deletes that file. Each layer is a struct of optional fields, so a new setting needs: a field in `Config` and `Layer` (language defaults to the system locale; `Config` has a manual `Default` because the session settings default to on), a setter on `ConfigStore` that writes to the right layer, a control on the settings page, and a matching option in `nix/module.nix`.

## Versioning and releases

Every push to `main` runs `.github/workflows/tag.yml`, which tags the newest commit via `.github/scripts/create-tags.sh` (`DRY_RUN=1 .github/scripts/create-tags.sh` previews locally) and then calls `release.yml` for that tag. The commits pushed with it are not tagged or released themselves, but each one counts towards the version, so the number is the same as if every commit had its own tag. (Tags pushed with the workflow's token are refused for a commit that changes a workflow file, which is why only the newest commit is tagged.) Commit messages decide the bump, and lower components reset to 0:

- `type!:`, `type(scope)!:` or a `BREAKING CHANGE:` footer: major
- `feat:` / `feat(scope):`: minor
- anything else: patch

Existing `vX.Y.Z` tags are respected (the running version resets to them), and with no tags it starts at `v0.0.0`. Because every push to `main` gets a release, prefer squash merges. `release.yml` patches the version in `[workspace.package]` of `Cargo.toml` from the tag at build time (not committed; the UI, backend and API crates share it) and publishes a Linux tarball, an AppImage and a Windows zip. Each contains all three executables, which have to stay next to each other.
